# Security model

Prime Work separates remote presentation from privileged local execution.

- The React renderer has no Node integration, is sandboxed and context-isolated, and communicates through a frozen narrow preload API. Packaged assets are served by a path-contained, MIME-fixed, CSP-protected `prime-work://app/` handler, allowing Electron's extra `file://` privileges fuse to remain disabled.
- Microphone permission is granted only to the exact authorized main renderer and only for audio; video, subframe checks, and every remote browser guest remain denied. Voice provider keys and optional self-hosted bearer tokens are encrypted with Electron `safeStorage` in a separate mode-0600 file, never returned across IPC, and may instead come from process environment variables. Persistent storage is fail-closed: macOS uses Keychain, Windows uses DPAPI, and Linux must provide a real desktop secret store such as GNOME Keyring/libsecret or KWallet; Electron's unprotected `basic_text` fallback and an unknown or unavailable backend are rejected with actionable setup guidance, and saved ciphertext is not decrypted or used until secure storage is available. When persistent secure storage is unavailable, a newly pasted key may be used for the current app session: after the save IPC completes it is held only in main-process memory, is never added to the secret file, returned by status IPC, or logged by the voice service, and is discarded when the app process exits. Self-hosted transcription uses a user-configured OpenAI-compatible endpoint: plain HTTP is restricted to loopback, remote hosts require HTTPS or an SSH tunnel, URL credentials/query/fragment data and redirects are rejected, and the optional token is attached only as a bearer header. Audio uploads, SDP, provider responses, local executable/model paths, tool arguments, and tool outputs are bounded and validated in the main process. Voice local context exposes OS time-zone and locale metadata plus a time-zone-derived approximate location hint; it does not request precise location permission. Each Realtime session is pinned to the harness selected when the orb opens: project discovery, model discovery, and task launch are restricted to that harness, and switching harnesses closes the orb. Voice model discovery returns only available models from providers currently visible in the GUI; hidden or disabled providers never enter fuzzy matching, and the selected model plus nearest supported reasoning level are revalidated by the runtime manager before the prompt. The Realtime orchestrator can start work only in an existing explicit project grant and only after the model emits `start_task`; the prompt is dispatched immediately without a second desktop confirmation.
- Every IPC call must come from the authorized main frame at the exact packaged renderer URL (or an explicitly validated loopback development URL). Authorization is revoked on navigation, renderer loss, close, and shutdown; outbound agent events repeat the exact URL check.
- Prime Agent runs out of process over strict-LF JSONL RPC. Credentials remain owned by Prime Agent. Commands and response-command correlations are validated. Runtimes, requests, in-flight bytes, record sizes, event counts, per-envelope bytes, and aggregate event bytes are capped.
- Quit closes IPC/process admission before taking cleanup snapshots. It then awaits RPC groups, one-shot utilities, PTYs, and captured PTY descendants through TERM/KILL escalation. Regression tests cover hostile children and background terminal jobs.
- Terminal processes are main-owned through `node-pty`; the renderer receives opaque IDs and bounded/coalesced byte streams. PTYs are project-authorized, owner-bound, count limited, and closed with their window/app.
- Persisted folders are explicit grants. Session-derived projects are display-only until the user selects them. Broad `/` and home roots are rejected; removal immediately revokes access and inferred dismissals persist. Folder identity uses inode plus filesystem birth time so a device-number change after remount can refresh the grant without accepting a replaced directory; legacy device/inode grants upgrade once only when the canonical path keeps its inode and its current birth time predates the original grant.
- Project configuration and file trees cannot escape canonical project roots. Symlinks and generated trees are excluded. Git/package/MCP mutations use validated fixed executables and argv arrays, never shell interpolation; settings writes use GooeyPi's cooperative lock, fingerprint-based conflict retries, pinned-directory checks, atomic replacement, and rollback. This is not a filesystem compare-and-swap: a same-user writer that ignores the lock can replace the file after the final fingerprint check and race GooeyPi's rename, so that writer's update may be overwritten. GooeyPi only writes local stdio MCP definitions for OMP and Pi when the canonical `npm:pi-mcp-adapter` package (optionally at an exact semantic version) is enabled; lookalike scoped/Git/local sources never satisfy admission. Pi adapter transitions and MCP writes share an agent-level cross-instance lock and re-check adapter state under that lock; definition removal remains available after the adapter is disabled and re-verifies the pinned project directory before and after reading each update snapshot. HTTP, SSE, and any URL-bearing MCP definition—including loopback—fail closed at service and settings-writer boundaries; the main-process RPC manager rejects auth slash commands for prompt, steer, follow-up, and heartbeat delivery, including every resume request regardless of observed heartbeat status. Schedules check prompts at create, update, resume, and run-now admission before project validation or queuing; startup blocks forbidden persisted active schedules before missed-run recovery and timer arming, leaves paused records available for cleanup and later resume validation, and the executor repeats the check as defense in depth. Session-daemon follow-up, voice tasks, collaboration creation, and peer delivery preflight the same policy before queuing, wake-up, or runtime start. Externally configured network entries remain visible but unavailable and may only be removed for cleanup. MCP rows use an independent 2,500-definition-per-settings-file discovery budget with an explicit truncation warning; unrelated catalog records cannot consume that budget. Local OMP/Pi definitions whose exact key cannot pass the bounded state API remain visible but non-actionable, with state management delegated to the harness and bounded exact removal retained. Definition removal uses a separate bounded exact key, never uninstalls an associated package, and never reads/deletes a shared Prime credential. Prime model discovery receives an MCP-blind credential facade. GooeyPi does not inspect or change MCP credentials; authorization cleanup stays with the harness because the app cannot prove credential provenance. This is an app admission guarantee, not a claim that the independently configured harness cannot load remote MCP. Linked-worktree grants require an exact match in Git's bounded worktree catalog, and new worktree destinations come from the native save dialog before their stable directory identity is persisted.
- Package installation uses one main-process source validator before dispatching to Prime, OMP, or Pi. Registry specs and existing absolute local paths remain supported; remote URL sources must use HTTPS or SSH. Plain HTTP follows the self-hosted-service contract and is accepted only for loopback hosts, while the unauthenticated `git://` transport is rejected even on loopback.
- Remote pages use `persist:prime-work-browser` with Node/preloads disabled. Popups and permissions are denied; URLs, redirects, frames, and downloads are credential-free HTTP(S). Downloads require a gesture, are limited to 512 MiB each, three concurrent, and 1 GiB/hour, and are canceled with their guest, browser reset, or app quit. When save prompting is disabled, downloads use a unique sanitized filename in the OS Downloads folder rather than being blocked or overwriting an existing name.
- Session JSONL is sensitive and read-only. Prime Work never rewrites transcripts; file paths, sizes, record counts, and catalog size are bounded. Model Markdown disables raw HTML and remote image loads.
- Pet discovery is read-only and bounded to non-symlinked packages beneath `~/.codex/pets`. Manifests, identifiers, text, and spritesheet sizes are validated in the main process; the bundled Orb and GooeyPi assets do not require Codex or Codex Pets to be installed.
- A single-instance lock and atomic/fsynced persistence prevent competing desktop processes from losing state.
- Project grants are harness-scoped in state version 4. Only explicitly recognized pre-harness v1/v2 project records and v2 schedule records with an absent harness migrate to Prime; schedules did not exist in v1, and v3/v4 project or schedule records with an absent or unknown harness are dropped. The authority is stored in `prime-work-state-v4.json`. On POSIX systems, the first v4 launch imports `prime-work-state.json`, file-fsyncs and atomically publishes v4, directory-fsyncs the publication, then renames the legacy file to a byte-exact `.migrated-v4-*` backup and directory-fsyncs that retirement; a failed retirement sync restores and syncs the legacy filename before startup fails. Fresh installs have no authority transition and do not require directory-fsync support.
- Windows does not expose durable directory-entry flushes through Node's supported filesystem APIs, so migration uses an explicit compatibility protocol instead of claiming POSIX rename durability. GooeyPi file-fsyncs a byte-exact unique backup, atomically replaces the legacy path with a version-3 marker containing zero projects and schedules, file-fsyncs and atomically publishes v4, then publishes a completed zero-authority marker. A pending marker is retryable from its named backup; a completed marker with a missing or corrupt v4 file fails closed rather than restoring possibly stale grants. Every v4 startup quarantines any non-marker file recreated at the legacy path before readiness. Older released binaries can parse the marker but see no project or schedule authority. Because a power loss can still make a Windows rename's directory entry uncertain, backups and markers are retained and startup errors report the exact files to preserve and retry.
- A state version newer than the running build, or a state file too large to classify safely, is opened read-only and left byte-for-byte unchanged. On Windows, any separate recreated legacy authority is still quarantined before readiness fails. A compatible GooeyPi build or explicit operator recovery is required before startup can continue.
- Durable automations are owned by Prime Work and persisted in the same bounded atomic state store. Every execution revalidates its explicitly granted project and, for thread tasks, its canonical session path before launching Prime Agent; concurrent writes to one thread are serialized. Missed occurrences are recorded as skipped rather than replayed.
- The bundled `prime-work-schedules` skill talks only to a random-token-authenticated loopback broker. Broker credentials are injected into the scoped Prime Agent runtime, requests are size/content-type bounded, and every operation is constrained to that runtime's authorized project and current session. The renderer never receives the broker token.
- Agent browser and terminal-read control use the same loopback-broker pattern: the bundled `prime-work-browser` extension receives a per-runtime random bearer token and can only act on browser tabs or read the active terminal belonging to that runtime's session (bound at spawn or first handshake, never rebound). Tabs are hardened `persist:prime-work-browser` webview guests; the main process only accepts guest bindings that passed the `will-attach-webview` gate, restricts agent navigation to credential-free HTTP(S), caps tabs per session and in total, rate-limits and size-bounds broker calls, and serializes input actions per tab. Page and terminal data returned to the agent are fenced as untrusted content; the renderer never receives the broker token.
- Top-level session collaboration uses a separate random-token loopback broker. Its immutable claim includes the source harness and canonical session path; targets and agent-created sessions must be different, non-archived top-level sessions in the same harness and canonical working directory. A multi-folder workspace does not widen that scope to sibling roots. Reads are bounded and use the owning read-only `SessionService`; sends and creation use the owning RPC manager. An offline target can be awakened only through the normal manager path, which revalidates its project grant and canonical session path. Agent model discovery exposes only available models from GUI-active providers, and creation revalidates the resolved model/reasoning plus any fast-mode request through the manager before launch; unsupported fast mode degrades to the normal service tier. Exact UUID validation, per-runtime rate limits, bounded prompts/messages/snapshots/waits, single-flight wakeups/creation, and model-only routing-block stripping prevent renderer-supplied titles or prompts from expanding authority. Incoming peer-message envelopes carry an app-local HMAC verified before transcript role elevation; the owner-only key is not provided to the renderer or harness. See `docs/session-collaboration.md`.
- Packaged fuses disable RunAsNode, `NODE_OPTIONS`, debug CLI arguments, browser-specific snapshot loading, and extra file-protocol privileges; cookie encryption, ASAR integrity, and OnlyLoadAppFromAsar are enabled. Each platform unpacks only the native runtime files it needs: macOS uses node-pty's `pty.node` and `spawn-helper` plus its architecture's ZeroMQ addon; Linux uses `pty.node` plus its architecture's bounded ZeroMQ ABI/libc fallback set; Windows uses the exact node-pty ConPTY/WinPTY `.node`, `.dll`, and helper `.exe` files plus its architecture's bounded ZeroMQ ABI fallback set. Release verification must reject any other unpacked path and check native architecture coverage before publication. Release gates cap main/preload bundles at 640/16 KiB, the initial renderer module graph at 1,280 KiB, each renderer JS/CSS chunk at 600 KiB, total renderer JS/CSS at 2.25 MiB, and packaged ASAR/app/installer/archive sizes under platform-specific release budgets. Signing entitlements retain only JIT and library-validation exceptions required by the Electron/native-module runtime; unsigned executable memory is not allowed.

Prime Agent packages, tools, terminals, configured MCP bridges, and the optional TryCUA driver execute with the user's OS permissions. GooeyPi never bundles or silently installs TryCUA: Computer Use is disabled by default, enabling it requires a runnable `cua-driver`, and new sessions receive only the detected absolute executable path plus GooeyPi's bundled non-MCP integration guidance. The toggle does not write MCP configuration. The desktop boundary protects the renderer and remote browser; it is not an OS sandbox for intentionally launched capabilities. Review projects, commands, and third-party integrations before granting access.

Public macOS distribution requires an external Developer ID Application identity plus Apple notarization and stapling. Signed Windows releases are opt-in until Authenticode credentials are configured; when enabled, Windows packaging fails closed unless an Authenticode identity is injected and verifies the packaged application, AppX/MSIX package, and NSIS installer before publication. An explicitly enabled unsigned beta path may publish the same Windows artifacts for testing, but those files are not trust-ready and will trigger SmartScreen or enterprise policy warnings. Verification asserts the expected signer, not merely a trusted one: the maintainer must set repository variable `GOOEYPI_WINDOWS_CERT_SUBJECT` (the certificate subject, matched exactly, e.g. `CN=Example Ltd, O=Example Ltd, C=GB`) and/or `GOOEYPI_WINDOWS_CERT_THUMBPRINT` (the certificate's 40-character SHA-1 thumbprint; spaces and colons are ignored, case-insensitive) alongside the `WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD` secrets. Both may be set, in which case both must match. A configured value that does not match the signing certificate fails the packaging job loudly; when neither is configured, public Windows packaging fails closed with an explicit message rather than accepting any certificate chain the runner happens to trust. GitHub Releases are built only from an existing semantic version tag whose version matches both package manifests and whose commit is on `main`; the final publishing job receives `contents: write` only after every enabled native package and verification job succeeds. Every published installer/archive is covered by `SHA256SUMS.txt` and a GitHub build-provenance attestation. Linux packages should additionally use repository signing metadata if package repositories are introduced. Local builds are not represented as trust-ready packages.

## Dependency pinning and supply chain

The release toolchain bootstraps the `packageManager`-pinned npm from the exact official archive checked into `vendor/`. Before invoking npm's installer, `scripts/release/bootstrap-npm.mjs` requires the version-derived repository path to be a regular non-symlink file and verifies its exact byte size and SHA-512 against `scripts/release/dependency-pins.json`. Every bootstrap then installs that absolute local archive with `--offline`, `--ignore-scripts`, `--no-audit`, and `--no-fund`; verifies the expected CLI, shim, and exact version; and only then publishes its shim directory to later GitHub Actions steps. The archive is a build-time tool and is excluded from packaged desktop applications.

This check authenticates the archive bytes against the reviewed Git history; it does not independently authenticate the extracted installation tree. The checked-out bootstrap code, invoking Node.js/npm processes, configured writable prefix, and local filesystem remain trusted. An attacker controlling any of those inputs can subvert installation or mutate files after verification. The provenance record in `vendor/npm-12.0.2.md` binds the vendored bytes to the npm registry metadata and upstream release tag. An npm upgrade must update the repository toolchain metadata, archive, provenance record, and artifact pin together under security-sensitive review.

`prime-agent`, `prime-agent-ai`, and their `@earendil-works/pi-*` transitive packages are third-party artifacts originally published to a `pub-*.r2.dev` bucket outside this project's control. They are **vendored**: the release tarballs live in `vendor/` in this repository (verified byte-for-byte against the previously trusted lockfile hashes at vendoring time, 2026-08-07) and are installed via `file:` specifiers plus npm `overrides`, so installs never fetch them from the network. Git history is the integrity boundary; the publisher's bucket being throttled, mutated, or deleted can no longer affect installs. The residual risk is a lockfile regeneration silently re-anchoring to swapped tarball bytes in the working tree — see the pin guard below. Treat any change to `vendor/`, the `prime-agent` lockfile entries, or the pin file as a security-sensitive review item: it must be an intentional upgrade with tarballs verified against the publisher.

Because Dependabot cannot parse these tarball specifiers, advisory coverage comes from a scheduled workflow (`.github/workflows/audit.yml`) that runs `npm run audit:production` weekly (plus on demand) and fails on high or critical advisories in the production dependency tree.

Some advisories have no patched release to move to, and a gate that fails every run stops carrying information: a genuinely new advisory would look exactly like the standing one. `scripts/release/audit-exceptions.json` therefore records the accepted advisories, each with the package it affects, a reason, and a mandatory expiry date. The audit fails on any advisory not on that list, on an accepted advisory whose expiry has passed (so acceptance cannot quietly become permanent), and on a stale exception that no longer matches anything (so a suppression cannot outlive the advisory it covered). `tests/release-scripts.test.ts` additionally fails once a checked-in expiry is in the past, surfacing it in ordinary CI rather than only in the weekly job. Adding or extending an exception is a security-sensitive review item: prefer upgrading, overriding, or vendoring a patched copy first. Longer term, the tarballs should move to a registry (private npm or GitHub Packages) or an immutable, versioned bucket behind a custom domain so that version-to-content bindings cannot change out from under the lockfile.

Silent re-anchoring is guarded by `scripts/release/dependency-pins.json`: every non-registry dependency's `resolved` location and `integrity` hash from the lockfile is mirrored there, executable bootstrap artifacts carry strict version/path/source/size/license/integrity metadata, and tests in `tests/release-scripts.test.ts` hash the actual `vendor/*.tgz` bytes. A regenerated lockfile or a swapped tarball therefore cannot pass CI without a matching, reviewable pin-file change in the same commit. To upgrade Prime Agent deliberately: obtain and verify the new tarballs against the publisher, replace them in `vendor/`, update `package.json`/`package-lock.json`, and mirror the new values into the pin file together.
