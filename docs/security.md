# Security model

GooeyPi separates remote presentation from privileged local execution.

For vulnerability intake and response expectations, follow the repository's [vulnerability reporting policy](../.github/SECURITY.md). Do not put suspected vulnerability details in a public issue, discussion, or pull request.

- The React renderer has no Node integration, is sandboxed and context-isolated, and communicates through a frozen narrow preload API. Packaged assets are served by a path-contained, MIME-fixed, CSP-protected `prime-work://app/` handler, allowing Electron's extra `file://` privileges fuse to remain disabled. The packaged protocol response and development HTML use the same CSP directives, checked by [renderer security tests](../tests/unit/renderer-csp.test.ts). Inline styles are allowed; script and connection access remains restricted. [renderer-security.ts](../electron/main/renderer-security.ts) defines renderer URL authorization.
- Microphone permission is granted only to the exact authorized main renderer and only for audio; video, subframe checks, and every remote browser guest remain denied. Voice provider keys and optional self-hosted bearer tokens are encrypted with Electron `safeStorage` in a separate mode-0600 file, never returned across IPC, and may instead come from process environment variables. Persistent storage is fail-closed: macOS uses Keychain, Windows uses DPAPI, and Linux must provide a real desktop secret store such as GNOME Keyring/libsecret or KWallet; Electron's unprotected `basic_text` fallback and an unknown or unavailable backend are rejected with actionable setup guidance, and saved ciphertext is not decrypted or used until secure storage is available. When persistent secure storage is unavailable, a newly pasted key may be used for the current app session: after the save IPC completes it is held only in main-process memory, is never added to the secret file, returned by status IPC, or logged by the voice service, and is discarded when the app process exits. Self-hosted transcription uses a user-configured OpenAI-compatible endpoint: plain HTTP is allowed on this computer and private-network addresses, while public hosts require HTTPS, URL credentials/query/fragment data and redirects are rejected, and the optional token is attached only as a bearer header. Audio uploads, SDP, provider responses, local executable/model paths, tool arguments, and tool outputs are bounded and validated in the main process. Voice local context exposes OS time-zone and locale metadata plus a time-zone-derived approximate location hint; it does not request precise location permission. Each Realtime session is pinned to the harness selected when the orb opens: project discovery, model discovery, and task launch are restricted to that harness, and switching harnesses closes the orb. Voice model discovery returns only available models from providers currently visible in the GUI; hidden or disabled providers never enter fuzzy matching, and the selected model plus nearest supported reasoning level are revalidated by the runtime manager before the prompt. The Realtime orchestrator can start work only in an existing explicit project grant and only after the model emits `start_task`; the prompt is dispatched immediately without a second desktop confirmation.
- Every IPC call must come from the authorized main frame at the exact packaged renderer URL (or an explicitly validated loopback development URL). Authorization is revoked on navigation, renderer loss, close, and shutdown; outbound agent events repeat the exact URL check.
- Prime Agent, OMP, and Pi run out of process over bounded JSONL RPC. Credentials remain in the owning harness format. Commands and response-command correlations are validated. Runtimes, requests, in-flight bytes, record sizes, event counts, per-envelope bytes, and aggregate event bytes are capped.
- Quit closes IPC/process admission before taking cleanup snapshots. It then awaits RPC groups, one-shot utilities, PTYs, and captured PTY descendants through TERM/KILL escalation. Regression tests cover hostile children and background terminal jobs.
- Terminal processes are main-owned through `node-pty`; the renderer receives opaque IDs and bounded/coalesced byte streams. PTYs are project-authorized, owner-bound, count limited, and closed on renderer reload or navigation, owner loss, window close, and app shutdown.
- Persisted folders are explicit grants. Session-derived folders receive a read-only grant at discovery for file listing, Git status/diff/branch, and path reveal; agent execution, terminals, mutating Git, worktrees, plugins, and configuration require an explicit persisted grant. Filesystem roots, home, and ancestors of home are rejected; removal immediately revokes access and inferred dismissals persist. Folder identity uses inode plus filesystem birth time so a device-number change after remount can refresh the grant without accepting a replaced directory; legacy device/inode grants upgrade once only when the canonical path keeps its inode and its current birth time predates the original grant.
- Project configuration and file trees cannot escape canonical project roots. Symlinks and generated trees are excluded. Git/package/MCP mutations use validated fixed executables and argv arrays, never shell interpolation; settings writes use GooeyPi's cooperative lock, fingerprint-based conflict retries, pinned-directory checks, atomic replacement, and rollback. This is not a filesystem compare-and-swap: a same-user writer that ignores the lock can replace the file after the final fingerprint check and race GooeyPi's rename, so that writer's update may be overwritten. Linked-worktree grants require an exact match in Git's bounded worktree catalog, and new worktree destinations come from the native save dialog before their stable directory identity is persisted as additional folders of the granting project rather than as a separate project.
- On Windows, Git resolves to an absolute `git.exe` from an absolute PATH directory outside the project, including after canonicalization. A repository-local executable cannot replace Git through the child working directory. The resolution and restricted Git environment live in [`process-utils.ts`](../electron/main/process-utils.ts).
- Package installation uses one main-process source validator before dispatching to Prime, OMP, or Pi. Registry specs and existing absolute local paths remain supported; remote URL sources must use HTTPS or SSH. Package-source plain HTTP is accepted only for loopback hosts, and the unauthenticated `git://` transport is rejected even on loopback.
- Remote pages use `persist:prime-work-browser` with Node/preloads disabled. Popups and permissions are denied; URLs, redirects, frames, and downloads are credential-free HTTP(S). Downloads require a gesture, are limited to 512 MiB each, three concurrent, and 1 GiB/hour, and are canceled with their guest, browser reset, or app quit. When save prompting is disabled, downloads use a unique sanitized filename in the OS Downloads folder rather than being blocked or overwriting an existing name.
- Session JSONL is sensitive. Catalog and transcript reads are bounded and read-only, but explicit offline rename can append metadata or rewrite a file through atomic replacement. Each list enumerates current files and may reuse unchanged per-file metadata; it is not a persistent cached session-list result. Model Markdown disables raw HTML and remote image loads.
- Pet discovery is read-only and bounded to non-symlinked packages beneath `~/.codex/pets`. Manifests, identifiers, text, and spritesheet sizes are validated in the main process; the bundled Orb and GooeyPi assets do not require Codex or Codex Pets to be installed.
- A single-instance lock and atomic/fsynced persistence prevent competing desktop processes from losing state.
- Project grants are harness-scoped in state version 4. Only explicitly recognized pre-harness v1/v2 project records and v2 schedule records with an absent harness migrate to Prime; schedules did not exist in v1, and v3/v4 project or schedule records with an absent or unknown harness are dropped. The authority is stored in `prime-work-state-v4.json`. On POSIX systems, the first v4 launch imports `prime-work-state.json`, file-fsyncs and atomically publishes v4, directory-fsyncs the publication, then renames the legacy file to a byte-exact `.migrated-v4-*` backup and directory-fsyncs that retirement; a failed retirement sync restores and syncs the legacy filename before startup fails. Fresh installs have no authority transition and do not require directory-fsync support.
- Windows does not expose durable directory-entry flushes through Node's supported filesystem APIs, so migration uses an explicit compatibility protocol instead of claiming POSIX rename durability. GooeyPi file-fsyncs a byte-exact unique backup, atomically replaces the legacy path with a version-3 marker containing zero projects and schedules, file-fsyncs and atomically publishes v4, then publishes a completed zero-authority marker. A pending marker is retryable from its named backup; a completed marker with a missing or corrupt v4 file fails closed rather than restoring possibly stale grants. Every v4 startup quarantines any non-marker file recreated at the legacy path before readiness. Older released binaries can parse the marker but see no project or schedule authority. Because a power loss can still make a Windows rename's directory entry uncertain, backups and markers are retained and startup errors report the exact files to preserve and retry.
- A state version newer than the running build, or a state file too large to classify safely, is opened read-only and left byte-for-byte unchanged. On Windows, any separate recreated legacy authority is still quarantined before readiness fails. A compatible GooeyPi build or explicit operator recovery is required before startup can continue.
- Durable automations are owned by GooeyPi and persisted in the same bounded atomic state store. Every execution revalidates its explicitly granted project and, for thread tasks, its canonical session path before launching the owning harness; concurrent writes to one thread are serialized. Missed occurrences are recorded as skipped rather than replayed. Recurrence expansion runs in a bounded worker; a bad persisted rule blocks its own current task instead of hanging the main event loop.
- The bundled `prime-work-schedules` skill talks only to a random-token-authenticated loopback broker. Broker credentials are injected into the scoped Prime Agent runtime, requests are size/content-type bounded, and every operation is constrained to that runtime's authorized project and current session. The renderer never receives the broker token. Packaged builds run the skill's Python from `<userData>/bundled-skills/prime-work-schedules` rather than from the signed bundle, because Prime Agent editable-installs and imports it and CPython would otherwise write bytecode into the sealed app; startup rebuilds that copy from the bundle whenever their content digests differ (ignoring `__pycache__`), and uses the bundled path for that launch if the copy fails.
- Agent browser and terminal-read control use the same loopback-broker pattern: the shared [`omp-work-browser.ts`](../assets/extensions/omp-work-browser.ts) extension receives a per-runtime random bearer token and can only act on browser tabs or read the active terminal belonging to that runtime's session (bound at spawn or first handshake, never rebound). Tabs are hardened `persist:prime-work-browser` webview guests; the main process only accepts guest bindings that passed the `will-attach-webview` gate, restricts agent navigation to credential-free HTTP(S), caps tabs per session and in total, rate-limits and size-bounds broker calls, and serializes input actions per tab. Browser capability also grants the bounded `terminal_read` tool for the same runtime session. Page and terminal data returned to the agent are fenced as untrusted content, and delimiter-like text in the payload is neutralized so it cannot close the fence; the renderer never receives the broker token.
- Top-level session collaboration uses a separate random-token loopback broker. Its immutable claim includes the source harness and canonical session path; targets and agent-created sessions must be different, non-archived top-level sessions in the same harness and canonical working directory. A multi-folder workspace does not widen that scope to sibling roots. Reads are bounded and use the owning `SessionService` read path; sends and creation use the owning RPC manager. An offline target can be awakened only through the normal manager path, which revalidates its project grant and canonical session path. Agent model discovery exposes only available models from GUI-active providers, and creation revalidates the resolved model/reasoning plus any fast-mode request through the manager before launch; unsupported fast mode degrades to the normal service tier. Exact UUID validation, per-runtime rate limits, bounded prompts/messages/snapshots/waits, single-flight wakeups/creation, and model-only routing-block stripping prevent renderer-supplied titles or prompts from expanding authority. Incoming peer-message envelopes carry an app-local HMAC verified before transcript role elevation; the owner-only key is not provided to the renderer or harness. See [session collaboration](session-collaboration.md).
- Packaged fuses disable RunAsNode, `NODE_OPTIONS`, debug CLI arguments, browser-specific snapshot loading, and extra file-protocol privileges; cookie encryption, ASAR integrity, and OnlyLoadAppFromAsar are enabled. Each platform unpacks only the native runtime files it needs: macOS uses node-pty's `pty.node` and `spawn-helper` plus its architecture's ZeroMQ addon; Linux uses `pty.node` plus its architecture's bounded ZeroMQ ABI/libc fallback set; Windows uses the exact node-pty ConPTY/WinPTY `.node`, `.dll`, and helper `.exe` files plus its architecture's bounded ZeroMQ ABI fallback set. Release verification must reject any other unpacked path and check native architecture coverage before publication. Bundle and package limits are defined in [`size-budgets.mjs`](../scripts/release/size-budgets.mjs); verification uses those values instead of documentation copies. Signing entitlements retain only JIT and library-validation exceptions required by the Electron/native-module runtime; unsigned executable memory is not allowed.
- Packaged builds accept one documented diagnostic argument, `--packaged-smoke=<absolute marker path>`, used by CI and pre-upload release verification to prove that a packaged application actually boots. It grants no capability and adds no IPC channel: the application starts exactly as it normally does and only after the renderer's own bootstrap completes an authorized `app:get-meta` invoke — which requires the main frame to be at the trusted packaged renderer URL and already authorized by the ordinary IPC trust gate — does main write a mode-0600, size-capped readiness marker and quit. The argument is read only from the first instance's own command line, never from a `second-instance` command line, is ignored outside packaged builds, and is rejected unless it names an absolute single-line path. Because readiness comes from the application itself, the inspect, `RunAsNode`, ASAR-integrity, and OnlyLoadAppFromAsar fuses stay at their shipped settings for the binaries under test.

Prime Agent packages, tools, terminals, configured MCP bridges, and the optional TryCUA driver execute with the user's OS permissions. GooeyPi never bundles or silently installs TryCUA: Computer Use is disabled by default, enabling it requires a runnable `cua-driver`, and new sessions receive only the detected absolute executable path plus GooeyPi's bundled non-MCP integration guidance. The toggle does not write MCP configuration. The desktop boundary protects the renderer and remote browser; it is not an OS sandbox for intentionally launched capabilities. Review projects, commands, and third-party integrations before granting access.

Public macOS distribution requires an external Developer ID Application identity plus Apple notarization and stapling. Signed Windows releases are opt-in until Authenticode credentials are configured; when enabled, Windows packaging fails closed unless an Authenticode identity is injected and verifies the packaged application, AppX/MSIX package, and NSIS installer before publication. An explicitly enabled unsigned beta path may publish the same Windows artifacts for testing, but those files are not trust-ready and will trigger SmartScreen or enterprise policy warnings. Verification asserts the expected signer, not merely a trusted one: the maintainer must set repository variable `GOOEYPI_WINDOWS_CERT_SUBJECT` (the certificate subject, matched exactly, e.g. `CN=Example Ltd, O=Example Ltd, C=GB`) and/or `GOOEYPI_WINDOWS_CERT_THUMBPRINT` (the certificate's 40-character SHA-1 thumbprint; spaces and colons are ignored, case-insensitive) alongside the `WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD` secrets. Both may be set, in which case both must match. A configured value that does not match the signing certificate fails the packaging job loudly; when neither is configured, public Windows packaging fails closed with an explicit message rather than accepting any certificate chain the runner happens to trust. GitHub Releases are built only from an existing semantic version tag whose version matches both package manifests and whose commit is on `main`; the final publishing job receives `contents: write` only after every enabled native package and verification job succeeds. Every published installer/archive is covered by `SHA256SUMS.txt` and a GitHub build-provenance attestation. Linux packages should additionally use repository signing metadata if package repositories are introduced. Local builds are not represented as trust-ready packages.

## MCP configuration and admission

GooeyPi only writes local stdio MCP definitions for OMP and Pi when the canonical `npm:pi-mcp-adapter` package (optionally at an exact semantic version) is enabled; lookalike scoped/Git/local sources never satisfy admission. Pi adapter transitions and MCP writes share an agent-level cross-instance lock and re-check adapter state under that lock; definition removal remains available after the adapter is disabled and re-verifies the pinned project directory before and after reading each update snapshot. HTTP, SSE, and any URL-bearing MCP definition—including loopback—fail closed at service and settings-writer boundaries; the main-process RPC manager rejects auth slash commands for prompt, steer, follow-up, and heartbeat delivery, including every resume request regardless of observed heartbeat status. Schedules check prompts at create, update, resume, and run-now admission before project validation or queuing; startup blocks forbidden persisted active schedules before missed-run recovery and timer arming, leaves paused records available for cleanup and later resume validation, and the executor repeats the check as defense in depth. Session-daemon follow-up, voice tasks, collaboration creation, and peer delivery preflight the same policy before queuing, wake-up, or runtime start. Externally configured network entries remain visible but unavailable and may only be removed for cleanup. MCP rows use an independent 2,500-definition-per-settings-file discovery budget with an explicit truncation warning; unrelated catalog records cannot consume that budget. Local OMP/Pi definitions whose exact key cannot pass the bounded state API remain visible but non-actionable, with state management delegated to the harness and bounded exact removal retained. Definition removal uses a separate bounded exact key, never uninstalls an associated package, and never reads/deletes a shared Prime credential. Prime model discovery receives an MCP-blind credential facade. GooeyPi does not inspect or change MCP credentials; authorization cleanup stays with the harness because the app cannot prove credential provenance. This is an app admission guarantee, not a claim that the independently configured harness cannot load remote MCP.

The canonical writer is [`plugins/mcp.ts`](../electron/main/plugins/mcp.ts).
Every mutation resolves and pins its target, takes a cooperative lock, checks
file fingerprints, and performs atomic replacement with rollback. User-scope
settings symlinks retain their link and update the resolved file. Project
configuration directories and settings files reject symlinks. A failed rollback
keeps the original recovery backup and reports its path.

A lock is recovered only when its owner is provably dead, or when it is a
branded GooeyPi lock from this process whose active token has been released.
Live owners and unknown native lock directories remain intact. Age alone does
not establish that a writer has stopped. These checks cannot make a cooperating
lock into filesystem compare-and-swap against an arbitrary same-user writer.

## Dependency pinning and supply chain

The release toolchain bootstraps the `packageManager`-pinned npm from the exact official archive checked into `vendor/`. Before invoking npm's installer, `scripts/release/bootstrap-npm.mjs` requires the version-derived repository path to be a regular non-symlink file and verifies its exact byte size and SHA-512 against `scripts/release/dependency-pins.json`. Every bootstrap then installs that absolute local archive with `--offline`, `--ignore-scripts`, `--no-audit`, and `--no-fund`; verifies the expected CLI, shim, and exact version; and only then publishes its shim directory to later GitHub Actions steps. The archive is a build-time tool and is excluded from packaged desktop applications.

This check authenticates the archive bytes against the reviewed Git history; it does not independently authenticate the extracted installation tree. The checked-out bootstrap code, invoking Node.js/npm processes, configured writable prefix, and local filesystem remain trusted. An attacker controlling any of those inputs can subvert installation or mutate files after verification. The provenance record in `vendor/npm-12.0.2.md` binds the vendored bytes to the npm registry metadata and upstream release tag. An npm upgrade must update the repository toolchain metadata, archive, provenance record, and artifact pin together under security-sensitive review.

Prime harness dependencies are vendored under [`vendor/`](../vendor/) and
installed through local `file:` specifiers and npm overrides. The installed
`prime-agent` and `prime-agent-ai` archives include GooeyPi-maintained patches;
they are not byte-for-byte copies of the upstream releases. Their
[Prime Agent](../vendor/prime-agent-0.7.0-gooeypi.1.md) and
[AI package](../vendor/prime-agent-ai-0.7.0-gooeypi.1.md) provenance records name
the trusted base archive, source patch, and patched artifact. Run
`npm run vendor:verify-patches` to verify those relationships and installed
contracts. The original base archives remain pinned as reference artifacts.

Git history and [`dependency-pins.json`](../scripts/release/dependency-pins.json)
form the integrity boundary. Changes to vendor bytes, their patches, lockfile
entries, or pins require supply-chain review. A deliberate upgrade updates the
artifacts and their provenance together.

Because Dependabot cannot parse these tarball specifiers, advisory coverage comes from the exception-aware `npm run audit:production` gate. [Pull-request CI](../.github/workflows/ci.yml) evaluates every exact PR head, the [release workflow](../.github/workflows/release.yml) evaluates its pinned commit before any package job, and the [scheduled workflow](../.github/workflows/audit.yml) continues to run weekly (plus on demand) so advisories disclosed after a merge are still detected.

Some advisories have no patched release to move to, and a gate that fails every run stops carrying information: a genuinely new advisory would look exactly like the standing one. `scripts/release/audit-exceptions.json` therefore records the accepted advisories, each with the package it affects, a reason, and a mandatory expiry date. The audit fails on any advisory not on that list, on an accepted advisory whose expiry has passed (so acceptance cannot quietly become permanent), and on a stale exception that no longer matches anything (so a suppression cannot outlive the advisory it covered). `tests/release-scripts.test.ts` additionally fails once a checked-in expiry is in the past, surfacing it in ordinary CI rather than only in the weekly job. Adding or extending an exception is a security-sensitive review item: prefer upgrading, overriding, or vendoring a patched copy first. Longer term, the tarballs should move to a registry (private npm or GitHub Packages) or an immutable, versioned bucket behind a custom domain so that version-to-content bindings cannot change out from under the lockfile.

Silent re-anchoring is guarded by `scripts/release/dependency-pins.json`: every non-registry dependency's `resolved` location and `integrity` hash from the lockfile is mirrored there, executable bootstrap artifacts carry strict version/path/source/size/license/integrity metadata, and tests in `tests/release-scripts.test.ts` hash the actual `vendor/*.tgz` bytes — including the two upstream base tarballs kept only for provenance, which are pinned in the same file under `reference-artifacts` and fail coverage checks if any vendored tarball is left unpinned. A regenerated lockfile or a swapped tarball therefore cannot pass CI without a matching, reviewable pin-file change in the same commit. To upgrade Prime Agent deliberately: obtain and verify the new tarballs against the publisher, replace them in `vendor/`, update `package.json`/`package-lock.json`, and mirror the new values into the pin file together.
